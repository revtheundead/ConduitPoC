# Stream Framing

[Back to index](index.md)

Stream-oriented transports (TCP, Serial) deliver a continuous byte stream with no inherent message boundaries. The `StreamFramer` reassembles this stream into complete protocol frames using sync patterns and length headers.

```cpp
#include <conduit/transceiver/stream_framer.hpp>
```

## When Framing Is Needed

| Transport | Stream? | Framing? |
|-----------|---------|----------|
| TCP Client | Yes | Required |
| TCP Server | Yes | Required |
| Serial | Yes | Required |
| UDP | No | Not needed (each datagram = one frame) |

The `Transceiver` automatically creates a `StreamFramer` for each stream-oriented peer. You only interact with `StreamFramer` directly when using manual session-level patterns (without the `Transceiver`).

## Algorithm

1. Append incoming bytes to an internal buffer
2. Search for the sync pattern at the buffer start; discard bytes before sync
3. If no sync pattern is configured, use length-prefix mode only (no sync search)
4. Check if the buffer contains at least `min_frame_header_size()` bytes
5. Call `extract_frame_length()` on the header to determine total frame length
6. If the buffer has enough bytes, extract the frame and remove it from the buffer
7. Repeat until no more complete frames can be extracted

The sync pattern, header size, and length extraction are provided by the `ISession` implementation (generated by bgen).

## StreamFramer API

### Construction

```cpp
// Default max buffer size (1 MB)
StreamFramer(traits::ISession& session);

// Custom max buffer size
StreamFramer(traits::ISession& session, size_t max_buffer_size);
```

The framer holds a reference to the session for its framing metadata (`sync_pattern()`, `min_frame_header_size()`, `extract_frame_length()`).

### push_data

```cpp
[[nodiscard]] Result<std::vector<std::vector<uint8_t>>>
    push_data(std::span<const uint8_t> data);
```

Appends `data` to the internal buffer and extracts all complete frames. Returns a vector of complete frames (each frame is a `vector<uint8_t>`). The returned vector may be empty if no complete frames are available yet.

### Other Methods

| Method | Returns | Description |
|--------|---------|-------------|
| `reset()` | `void` | Clear the internal buffer |
| `buffered_bytes()` | `size_t` | Bytes currently in the buffer (partial frame data) |
| `max_buffer_size()` | `size_t` | Maximum buffer size (default 1 MB) |
| `set_max_buffer_size(size_t)` | `void` | Change the maximum buffer size |

## Transceiver Integration

When you add a stream-oriented peer to the `Transceiver`, it automatically:

1. Creates a `StreamFramer` per peer, bound to the peer's `ISession`
2. Routes `on_data_received` through the framer
3. Feeds extracted frames to `session.decode_frame()`
4. Pushes decoded messages to the dispatch queue

You do not need to create or manage framers when using the `Transceiver`.

## Manual Usage

For direct transport/session control (without the `Transceiver`):

```cpp
auto session = my_protocol::create_frame_session();
auto framer = std::make_unique<StreamFramer>(*session);

// In your on_data_received callback:
auto frames = framer->push_data(incoming_bytes);
if (frames) {
    for (auto& frame : *frames) {
        auto decoded = session->decode_frame(frame);
        if (decoded) {
            for (auto& msg : *decoded) {
                handle(msg);
            }
        }
    }
}
```

See the [SentryLink example](sessions-and-codegen.md) for a complete manual usage pattern.

## Common Pitfalls

> **Pitfall:** One framer per peer. Each framer maintains internal buffer state. Sharing a framer between peers or feeding data from multiple sources into one framer corrupts the state.

> **Pitfall:** The framer is not thread-safe. Only one thread (the I/O thread) should call `push_data()`. The `Transceiver` ensures this automatically.

> **Pitfall:** If appending new data would cause the buffer to exceed `max_buffer_size`, the framer resets (clears the buffer) and returns a `BufferOverrun` error. This can happen if no valid sync pattern is found for an extended period (e.g., connecting mid-stream without a sync word). The caller should handle this error and continue feeding data -- the framer will resynchronize on the next valid sync pattern.

> **Pitfall:** A protocol with an empty sync pattern relies entirely on length-prefix framing. If the stream starts at an arbitrary point (not at a frame boundary), recovery is not possible without a sync word.
